02 / The Underlying Problem

Why Raw APIs, OAuth, and MCP Are Insufficient

Today's developer ecosystem equates exposing an API to an agent with providing an OpenAPI specification or Model Context Protocol (MCP) server. For stateful businesses, this causes catastrophic failure modes.

Phantom Reservations
Raw APIs lack stateful hold semantics. Agents query availability, ask the user, and attempt to book 5 minutes later. The slot was taken by a human user 4 minutes ago.
Retry Double-Debits
Autonomous agent frameworks retry failed tool calls automatically on HTTP 504 timeouts. Without distributed idempotency locks, retried tool calls result in multiple debit charges.
Untyped Upselling
Autonomous agents hallucinate or accept optional add-ons during multi-step checkout (e.g. ₹600 premium insurance or dry needling package) violating user budget ceilings.
Why Startups Do Not Build This Internally

A startup engineering team may ask: "Why can't our developers simply build an MCP server and add some custom middleware?" Exposing a tool endpoint takes an afternoon. Building safe, stateful, multi-agent transactional infrastructure requires eleven distinct distributed systems subsystems:

  • 1
    Business Workflow Redesign
    Deconstructing monolithic checkout endpoints into search, 2-phase holds, approval gates, and atomic settlement.
  • 2
    Delegated Authorization
    Enforcing fine-grained budget, time, and action constraints rather than all-or-nothing Bearer token scopes.
  • 3
    Distributed Idempotency
    Atomic Redis locking and IETF draft-9 idempotency cache to safely absorb unpredictable agent retry storms.
  • 4
    Automatic Hold Expiration
    Self-expiring inventory reservation leases with webhook notifications when abandoned agents fail to complete transactions.
  • 5
    State Reconciliation & Sagas
    Compensating actions when third-party payments clear but downstream booking confirmation fails midway.
  • 6
    Agent-Specific Conformance Testing
    Simulating adversarial LLM behavior: hallucinated prices, mutated payloads, duplicate replay bursts, and stale slots.
  • 7
    Cryptographic Audit Logs
    Tamper-evident signed receipts proving what user authorized, what agent requested, and what provider confirmed.
  • 8
    Capability Versioning
    Backward-compatible schema upgrades ensuring autonomous clients do not break when underlying APIs change.
  • 9
    Multi-Ecosystem Compatibility
    Simultaneous compilation to Model Context Protocol (MCP), Linux Foundation A2A, and REST OpenAPI specs.
  • 10
    Runtime Observability & Guardrails
    Real-time tracking of agent abandonment rates, hold-to-book ratios, latency budgets, and intent anomalies.
The Real Commercial Argument
The cost is not creating an MCP endpoint. The cost is maintaining safe behavior when probabilistic software interacts with stateful business systems.

04 / Product Architecture

The Four Core Modules of AgentFlow

AgentFlow operates as a high-performance proxy between autonomous agent ecosystems and backend service platforms, adding less than 18ms of p95 latency overhead.

1. AgentFlow Gateway
High-performance transaction proxy written in Go. Sits in front of the merchant backend to manage two-phase holds, atomic idempotency caching (IETF draft-9), automatic hold expiration, and saga compensation rollbacks when downstream providers fail.
2. AgentFlow Capability Builder
Visual developer workbench that ingests existing OpenAPI 3.x specifications and synthesizes stateful capability state machines, auto-generating compliant MCP servers, A2A endpoints, and /.well-known/agent-capability.json manifests.
3. AgentFlow Intent Policy
Deterministic policy engine that evaluates agent invocations against user-approved mandates. Enforces typed budget ceilings, single-action whitelists, expiration deadlines, and triggers out-of-band confirmation gates for high-risk operations.
4. AgentFlow Transaction Certification
Automated conformance test suite that executes adversarial integration tests against merchant staging environments (payload fuzzing, duplicate retries, hold timeouts, race conditions) before issuing cryptographic readiness certificates.
What AgentFlow Is NOT
  • Not an LLM Provider: We do not host, train, or tune foundation models.
  • Not a Generic Chatbot: We do not provide customer-facing chat UIs.
  • Not a Replacement for Stripe: We do not store card numbers or settle payments directly; we orchestrate Stripe/Razorpay.
  • Not a Replacement for Kong: We sit behind or alongside API gateways to manage business state, not L7 network routing.
  • Not a Proprietary Protocol: We support open standards (MCP, A2A, OpenAPI, IETF Idempotency).
  • Not a Medical Decision System: We handle administrative scheduling and booking only; zero clinical judgment.

Pragmatic 3-Tier Agent Identity Roadmap
Rather than relying on speculative hardware or model-weight attestation across heterogeneous consumer devices, AgentFlow employs a realistic progressive identity model:
Level 1: Application Identity (Production Ready)
Registered agent application account, OAuth 2.0 client credentials, or API keys issued to verified platforms.
Level 2: Cryptographic Session Identity (Production Ready)
Agent signs every request payload using an ephemeral Ed25519 session keypair. Eliminates token replay attacks.
Level 3: Attested Identity (Ecosystem Roadmap)
Hardware enclave or secure runtime attestation (AWS Nitro Enclaves, Apple Secure Enclave) when supported by client.

When autonomous agents fail or disconnect halfway through a checkout flow, the system must not leave slots locked or charge customer cards without booking tickets.

Autonomous agents introduce novel attack vectors that traditional WAFs and OAuth proxies are blind to. Here is our Threat → Control → Evidence defense architecture.

Prompt Injection in Review/Notes Payload field sanitation; prompt strings isolated from action control structures. Unit test suite & static AST validation log.
Tool-Description Poisoning Capability schemas cryptographically signed by provider; immutable runtime spec. Ed25519 signature verified on each discovery fetch.
Credential Theft & Replay Ephemeral session keypairs (PoP) and single-use confirmation challenge tokens. Token invalidation receipt in Redis state cache.
Duplicate Payment Retries IETF draft-9 idempotency key lock with atomic Redis distributed lease. Cached response payload returned with Idempotent-Replay: true.
Stale Availability Race Two-phase temporary hold leases with 10-minute automatic TTL expiration. Hold creation record #h_xxx with expiration timestamp.
Agent Impersonation Client app OAuth verification combined with ephemeral session challenge signing. Validated client certificate / OAuth token audit trail.
